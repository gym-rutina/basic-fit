# design-system/SYNC.md — claude.ai/design sync conventions

> **Do not run the standard nested package-build converter end-to-end
> against this repo.** It always emits the nested
> `components/<group>/<Name>/<Name>.{jsx,d.ts,prompt.md,html}` layout and
> would fork this project into two incompatible component layouts. See
> point 1 below.

This is the durable, checked-in record of how `design-system/` syncs with
claude.ai/design. `.design-sync/NOTES.md` is per-sync scratch state (rotating,
git-ignored — see `.gitignore`); this file is the permanent version of the
knowledge it captured for the 2026-08-21 sync, and supersedes its durable
content. Every point below traces back to a finding recorded there.

## 1. The flat-sibling layout is deliberate and current

`design-system/components/` uses **flat siblings**, not the standard
converter's nested shape:

- **This repo:** `components/<group>/<Name>.jsx` + `<Name>.d.ts` +
  `<Name>.prompt.md` sit directly next to each other (no
  `components/<group>/<Name>/` subdirectory), with one aggregate
  `<group>.card.html` preview card per group instead of one `<Name>.html`
  per component.
- **The standard converter** (`package-build.mjs`'s package-shape output)
  instead emits `components/<group>/<Name>/<Name>.{jsx,d.ts,prompt.md,html}`
  — a subdirectory per component.

This repo was hand/agent-authored directly in claude.ai/design's own
canvas/editor — not produced by the converter — then wrapped with
`SKILL.md`/`readme.md`/`ui_kits/`/`templates/` for reuse as a project skill.
Running the converter end-to-end here would restructure the whole live
project away from its current, working convention: a large, hard-to-reverse
change to a project the user actively builds with, and not something any
routine sync should trigger on its own. If a real migration to the nested
layout is ever wanted, that is a deliberate, separate decision made with the
user — never a sync side-effect.

## 2. Rebuild trigger

`design-system/_ds_bundle.js` must be rebuilt after **any** change to:

- `design-system/components/**/*.jsx`, or
- `design-system/tokens/*.css`

via the scoped-rebuild recipe (`.design-sync/NOTES.md`, "How the 2026-08-21
sync worked", steps 1–6) — never the full converter (point 1 above).

- Run **`npm run ds:check-bundle`** before a sync to detect staleness. It
  exits non-zero and names every source file newer than `_ds_bundle.js`;
  exit 0 and "design-system bundle is fresh." otherwise.
- Run **`npm run ds:fix-bundle`** after a rebuild to apply the post-process
  fixes in point 3.

## 3. Two converter behaviours that need post-processing every rebuild

The standard converter does two things unconditionally that don't fit this
repo, every single time it runs:

- **`globalName` underscore stripping.** `toNamespace()` in
  `package-build.mjs` strips non-alphanumeric characters when normalizing
  `cfg.globalName`, with no override available. The required name
  `BasicFitDesignSystem_1cb8a2` (matching `.design-sync/config.json`) comes
  out as `BasicFitDesignSystem1cb8a2` — missing the underscore before the
  project id. It must be restored everywhere it appears: the module's `var`
  declaration, the header's `namespace` field, and the final
  `window.<NS>=` assignment (7 occurrences in the real bundle).
- **Nested `sourcePath`/`sourceHashes`.** The header's `sourcePath` and
  `sourceHashes` keys point at the converter's own nested-output paths
  (`components/<group>/<Name>/<Name>.jsx`), not this repo's real flat paths
  (`components/<group>/<Name>.jsx`). They must be collapsed to match reality.

**`npm run ds:fix-bundle`** (`scripts/ds-bundle-postprocess.js`, core in
`scripts/lib/dsBundlePostprocess.js`) automates both fixes, plus stamping
`"format":4` as the header's first key (the established convention). It
reads `globalName`/`projectId` from `.design-sync/config.json` and fails
clearly instead of guessing them if that file is missing.

## 4. `_ds_manifest.json` is server-regenerated

`design-system/_ds_manifest.json` is regenerated by the server whenever the
project is opened in claude.ai/design. It must stay **excluded** from every
upload's `writes` — do not add it back to an upload without first confirming
that has changed.

## 5. No `_ds_sync.json` anchor — and that's expected

There is no `_ds_sync.json` sidecar for this project, and that is not a gap.
The anchor machinery assumes the standard nested output plus
`.design-sync/previews/` plus a capture pipeline, and this off-script flat
layout has no reliable `sourceKey`/`renderHash` recipe to hang an anchor on.
Per the base skill's own guidance, omitting it is the honest choice: **every
sync re-verifies and re-diffs everything from scratch** rather than trusting
a partial or misleading anchor.

## 6. Mandatory manual visual check before calling a sync done

Before treating any sync as complete: **open the project in
claude.ai/design and skim the Design System pane** for visual regressions —
wrong colors, broken layout, missing tokens at runtime.

The automated Node `vm` sanity check (point 7) only proves that the
compiled bundle's components don't throw when called with empty props. It
does not catch visual regressions and is **not** a substitute for looking at
the DS pane.

## 7. Keep `design-system/_ds_bundle.test.js` green

`design-system/_ds_bundle.test.js` is the F6-audit guard: it evaluates the
compiled bundle and fails if a regeneration silently drops a component from
the exported namespace (historical exports were assembled in execution
order, so a mis-ordered regeneration can lose one without erroring). It runs
as part of `npm test` — keep it green after any rebuild, before uploading.
